# Agent Note: 目录路由的实时模型发现与模型级协议

Status: implemented

[English](2026-09-23-live-catalog-discovery-and-per-model-protocol.md) | 中文

## Problem

本适配器出货的 pi-ai 目录是上游生成的快照，因此在快照之后新增模型的提供方会提供一个路由无法描述的 id：该模型永远不出现在列表中，而且把它加入目录路由会被拒绝，因为模型条目没有地方点名自己的协议或端点。已安装模型协议不一致的路由——`opencode-go` 从两个端点提供 Anthropic Messages、Chat Completions 与 Responses 模型——因此永远无法获得比快照更新的模型，文档记载的变通办法是每种协议一条路由。

Models 页面的获取操作让这一缺口变得不可见而非可操作：目录路由不发网络请求、直接由快照回答，这对容量是最好的答案，但对时效不是。没有任何东西去询问用户正看着的那个端点。

## Decision

`LlmModelDiscoveryRequest.live` 让询问在适配器已描述该路由时也去询问端点。Models 页面只从其获取操作发送它；为继承输入类型提供数据的自动目录读取仍只读注册表，因此打开卡片不产生网络请求，离线时也仍能渲染。目录路由上的实时回答会把端点列表与已安装元数据合并：列表决定路由提供哪些 id 及其顺序，已安装条目提供目录认识的每个 id 的名称、容量与输入模态，列表中缺失的目录模型则排在其后。路由使用最多的端点先被询问，第一个给出可读列表的端点即为回答者——询问每个端点会合并与路由已存凭据鉴权方式不同的列表，在 `opencode.ai` 上这会报告该套餐并不提供的超集。点名了自己端点的草稿则改为询问该端点；没有任何端点应答的实时询问会报告其失败，而不是返回它被要求刷新的那份快照。

`PiAiModelProfile` 新增 `api` 与 `baseURL`，各自优先于同名的路由级字段，因此一条路由可以服务多种协议格式。`buildProvider` 为模型点名的每种协议收集一个实现，并把映射交给本包自己的 `createProvider`；后者现在按 `model.api` 分发，并对没有实现的协议让该模型失败，而不是把它交给另一个协议。本构建无法服务的协议会在配置写入处被拒绝；已安装目录提供方未实现的协议会让请求以 pi-ai 自己的消息失败，因为 `Provider` 不暴露其协议映射。Models 页面在条目的高级折叠区渲染这两个字段，并复用路由级协议标签。

## Alternatives considered

**询问目录路由的每个端点并合并列表。** `https://opencode.ai/zen/go/v1/models` 对带鉴权的请求回答该套餐提供的 33 个模型，而对未鉴权或 `x-api-key` 请求回答 40 个模型的超集，因此并集报告的是该路由凭据无法服务的模型。首个应答端点让答案可描述、请求有界。

**由路由本身服务实时列表。** 所服务的目录将不再是设置事实：注册由配置派生，pi-ai 的提供方复用特意丢弃其自身的动态刷新，使后台刷新不会与设置文档矛盾，而运行中会话里变化的模型列表会改变请求可点名的内容。发现结果保持为界面显式采纳的候选元数据。

**从列出该模型的端点推断其协议。** 列表端点服务多种协议的模型——`opencode.ai` 的 `/v1/models` 包含由 Anthropic 服务的 id——因此推断会误标并过度声明；协议由用户为每个模型声明一次。

**把协议保持在路由级并每种协议拆一条路由。** 这是文档记载的变通办法；它为一个提供方增加多条路由与凭据引用，而且要在每条拆分路由上重述端点，才能表达模型协议不一致的路由。

## Consequences

对目录路由而言，获取操作现在是网络调用：更慢，而且可能在以前能回答的地方失败。这是刻意的——静默的陈旧答案正是本次改动要消除的缺陷——手工录入与由注册表支撑的继承提示仍是离线路径。每条路由只有一个端点应答，因此仅由同一路由的另一个端点服务的模型需要手工添加；这两个事实都记录在包的已知限制中。

目录路由的模型级协议在请求时而非写入时针对已安装提供方校验，因此误声明的协议会以点名提供方与协议的 pi-ai 消息失败。手工声明路由在配置写入处校验，因为适配器自己构建它们的实现。

验证：`tests/discovery.spec.ts` 覆盖实时合并、主端点、点名端点覆盖、下一端点回退与报告的首次失败；`tests/catalog.spec.ts` 覆盖模型级协议与端点解析、一条路由向两种协议格式的分发，以及空协议或不可服务协议的拒绝；`tests/config.spec.ts` 覆盖 schema 边界；`apps/web/tests/models-settings.e2e.ts` 覆盖目录路由的获取请求到达其端点，并在其 golden 中记录展开条目新增的控件；`tests/provider-form.client.spec.tsx` 覆盖请求形态与条目的协议、端点编辑。
